# 고정 계약을 세대별로 돌린 결과 (R2 #18, T4 #16)

`bike_spec.py` **한 벌**을 세대마다 다시 선언하지 않고 그대로 돌렸다. 계약이 무엇을
흡수하고 무엇에서 멈추는지가 R2의 관측값이다. 세대 정의는
[bike-source-generations.md](bike-source-generations.md).

빌더는 `0.4.0.dev0+66473fc598a3` (kpubdata-builder#621, coalesce/zfill/year_month).

| | rows_in | status | failed_stage | exception | offending_field | rows_out |
|---|---:|---|---|---|---|---:|
| G1 | 327,231 | ok | — | — | — | 327,231 |
| G2 | 3,200,206 | ok | — | — | — | 3,200,206 |
| I1 | 128,413 | ok | — | — | — | 128,413 |
| G3 | 1,246,386 | ok | — | — | — | 1,246,386 |
| G4 | 32,786 | **failed** | silver / coalesce | `TabularError` | `ym_raw` | 0 |
| T4 | 4,902,236 | ok | — | — | — | 4,902,236 |

행이 하나도 줄지 않았다. 계약에 `filters`가 없으므로 당연하지만, Silver가 품질 지표를
인위적으로 개선하는 경로가 없다는 것을 실측으로 확인한 것이기도 하다.

## G1 — 통과

세 선언이 모두 실제로 동작했다.

```
zfill        "3" → "00003",  "102" → "00102"
year_month   "2020-01" (dashed) 통과
coalesce     이동거리 → distance_m,  이용시간 → duration_min,  대여일자 → ym_raw
null_tokens  gender 114,718 / exercise_kcal 401 / carbon_kg 401
```

## I1 — 통과. **고정 계약이 일시적 헤더 이상을 흡수했다**

2021-09 한 달만 `이용거리(M)`·`이용시간(본)`로 나온다. 다음 달 원복되므로 영구적
진화가 아니라 incident다.

`distance_m`의 null이 **0**이다. 오타 헤더가 alias 후보로 받아들여져 값이 그대로
들어왔다는 뜻이다 — 컬럼이 통째로 비었다면 null이 128,413이었을 것이다.

이것을 "incident가 사라졌다"로 읽으면 안 된다. R2의 결과는 **고정된 선언 계약이 일시적
헤더 이상을 흡수했다**이고, 흡수한 이유는 그 표현이 계약에 alias로 이미 선언돼 있었기
때문이다. 선언에 없는 이상이었다면 멈췄을 것이다.

## G3 — 통과

시점 컬럼 이름(`대여년월`)과 표기(`202301`)가 동시에 바뀌는데 coalesce와 year_month가
각각 흡수했다. `성별`의 `\N`이 사라진 것도 그대로 관측된다 — null이 gender에 없다.

## G4 — fail-closed. **이것이 옳은 결과다**

```
TabularError: coalesce target 'ym_raw' found none of its candidates
              in the source: ['대여일자', '대여년월']
```

Bronze는 완료하고 Silver 정규화에서 멈췄다.

멈춘 지점이 `ym_raw`인 것은 계약이 컬럼을 보는 순서 때문이고, **실제 단절은 더 깊다.**
G4에는 대여소번호·성별·연령대코드가 아예 없고 `이용건수`가 `대여건수`/`반납건수`로
갈렸다. 단위가 `대여소×권종×성별×연령×월`에서 `대여소×월`로 바뀌었다.

`기준년월`을 후보에 추가하면 이 오류는 사라지지만 그 다음 오류가 나올 뿐이고, 무엇보다
**계약을 확장해 통과시키는 것 자체가 R2의 측정을 망친다.** 표현이 아니라 의미가 바뀐
소스에서 고정 계약이 멈추는 것이 이 실험이 보이려는 것이다.

## G2 — 통과. 한 컬럼 안에서 표기가 바뀌는데도

G2 내부에 `2022-01`과 `202207`이 섞여 있다. 산출물의 `ym_raw`는 **30개월이 전부
canonical `YYYY-MM`**이다. 세대를 쪼개지 않기로 한 판단이 여기서 값을 치렀고,
`year_month`가 그것을 흡수했다.

`station_code`의 길이는 전부 5다 — `00003`과 `102`가 섞여 들어왔지만 zfill 뒤에는
한 폭이다.

## 문서의 `\N` 수치를 고쳤다

[bike-source-generations.md](bike-source-generations.md)는 `\N`이 운동량·탄소량에
"각 229건"이라고 적었는데, **229는 어느 세대의 값도 아니었다.** 배포 CSV를 직접 세어
빌드 산출물의 null 수와 대조했고, 둘이 정확히 일치한다.

| | 성별 | 운동량 | 탄소량 |
|---|---:|---:|---:|
| G1 | 114,718 | 401 | 401 |
| G2 | 787,098 | 3,923 | 3,923 |
| I1 | 38,481 | 176 | 176 |
| G3 | **0** | 754 | 754 |
| T4 합 | 940,297 | 5,254 | 5,254 |

계약의 동작에는 영향이 없다(`null_tokens`는 개수와 무관하게 표기를 모은다). 문서만
고쳤다. 성별의 `\N`이 G3에서 사라진다는 문서의 서술은 사실이었다.

## 빌더 drift 탐지는 지금 노이즈다

빌더가 `dataset_id`를 키로 이전 빌드와 비교하는데, 지금 그 상대가 폐기한 API 기반
스냅샷이다(`row_count_jump 1832580 -> 327231`, `column_removed RNUM/START_INDEX`).
세대 간 비교가 아니므로, R2에서 drift 지표를 쓰려면 인덱스를 먼저 정리해야 한다.

## T4에서 막힌 것은 계약이 아니라 저장 계층이었다

첫 시도는 빌드가 시작되기도 전에 멈췄다.

```
sqlite3.DataError: string or blob too big
```

빌더가 딸려 보내는 `SQLiteUploadRepository`는 content를 BLOB으로 넣는데, SQLite의
기본 `SQLITE_MAX_LENGTH`가 10억 바이트(약 953 MiB)다. T4 통합본은 1,444 MiB다.
**G2가 945.6 MiB로 통과한 것이 우연이었다** — 8 MiB 차이였다.

세대 계약과는 무관하므로 위 표의 분류(1 구현 버그 / 2 선언 누락 / 3 새 원천 표현 /
4 semantic break) 어디에도 넣지 않는다. 빌더를 고치지도 않았다. 서비스가 업로드
크기에 상한을 두는 것은 맞고, 여기서 다루는 것은 사용자 업로드가 아니라 얼려 둔
실험 원천이다. `UploadRepository`가 Protocol이므로 harness가 저장 방식만 바꿔 끼웠다
(`scripts/_upload_store.py`). 빌더 코드도 Silver 계약도 그대로다.

### 남은 병목은 SQLite가 아니라 메모리다

지금 경로는 1.4 GiB jsonl을 통째로 읽어(`source.read_bytes()`) 저장소에 복사하고,
다시 레코드 리스트로 펼친 뒤 DataFrame을 만든다. SQLite 한계를 치웠어도 그 구조는
그대로라 더 큰 원천에서 다시 막힌다. 논문 범위에서는 T4가 최대라 지금 손대지 않는다.

빌더 쪽 개선 방향으로는 크기에 따라 저장소를 고르고(작은 것은 BLOB, 큰 것은
파일/오브젝트), 큰 파일은 streaming parser로 Bronze를 chunk 단위로 만드는 구조가
맞다. 나머지 파이프라인은 Protocol 뒤에 있으므로 저장 위치를 몰라도 된다.

## T4 통합본 — 통과. 그리고 문서에 없던 것이 하나 나왔다

```
4,902,236행, 16컬럼 → 11컬럼, 48개월 전부 canonical, station_code 폭 전부 5
distance_m / duration_min null 0
1070.0s
```

세대별 헤더의 합집합 16컬럼이 한 프레임에 들어온다 — `이동거리`/`이동거리(M)`/
`이용거리(M)`가 동시에 존재한다. **coalesce 충돌이 한 건도 없었다.** 세대가 겹치지
않으므로 행마다 한쪽만 non-null이어야 하는데 그것이 실제로 성립했다는 뜻이고, 세대
경계를 헤더로 가른 판단이 여기서 검증됐다.

null 수도 세대별 합과 정확히 일치한다 (gender 940,297 = 114,718+787,098+38,481+0,
exercise_kcal 5,254). 통합 과정에서 값이 새거나 겹치지 않았다.

### 계약이 남기기로 한 것은 실제로 남았다

`age_band`에 두 코드 체계가 그대로 공존한다.

```
'10대', '20대', ..., '70대이상', 'AGE_001', 'AGE_002', ...
```

`gender`도 `F`/`M`/`f`/`m`이 그대로다(`m` 835건, `f` 390건). 매핑하지 않기로 한 결정이
말로만이 아니라 산출물에서 확인된다.

### **성별의 결측 표기가 하나가 아니라 둘이었다** (새 발견)

문서는 성별 결측을 `\N` 하나로 적었다. 실제로는 빈 문자열이 함께 온다 — 같은 파일,
같은 달에 둘 다 나온다. 배포 CSV 원문에서 직접 확인했으므로 ingest가 만든 것이 아니다.

| | 빈 문자열 | `\N` | 값 있음 | 결측 비율 |
|---|---:|---:|---:|---:|
| G1 | 54,390 | 114,718 | 158,123 | 51.7% |
| G2 | 560,516 | 787,098 | 1,852,592 | 42.1% |
| I1 | 16,833 | 38,481 | 73,099 | 43.1% |
| G3 | 409,045 | **0** | 837,341 | 32.8% |
| T4 | 1,040,784 | 940,297 | 2,921,155 | **40.4%** |

**빈 문자열 쪽이 더 많다.** 그리고 G3에서 사라진 것은 `\N`뿐이고 빈 문자열은 48개월
전부에 남아 있다 — 문서의 "G3: 성별 결측 없음"은 `\N`만 본 서술이었다. 고쳤다.

계약은 `null_tokens`에 `\N` 하나만 선언했으므로 빈 문자열은 **값으로 남았다.**
산출물의 `gender`에 `''`가 1,040,784건 있다.

### 이것을 고치지 않는다 (지금은)

분류 3(새로 발견된 source representation)이므로 근거부터 본다.

`null_tokens`에 `""`를 더하면 빈 문자열이 null이 된다. 다만 `null_tokens`는 컬럼별이
아니라 **모든 Utf8 컬럼에 걸리는 전역 선언**이라, `station_name`을 비롯한 다른 컬럼의
빈 문자열까지 함께 null이 된다. 성별 하나 때문에 계약 전체의 결측 정의를 바꾸는 셈이다.

그리고 `gender`는 `required`가 아니고 T4가 쓰지 않는다. 품질 지표(missing_rate /
schema_conformance)는 required 컬럼에 대해서만 정의되므로 표 2의 숫자는 이것에
영향받지 않는다.

오히려 이대로가 논문에 쓸 만한 사례다 — **결측 표기가 하나가 아닌데 하나만 선언하면,
나머지는 조용히 "값"으로 남는다.** 40.4%의 결측 중 절반이 계약이 선언하지 않았다는
이유로 결측으로 세어지지 않는다. "Silver 계약이 선언한 것만 보장한다"가 무슨 뜻인지
보여 주는 실측이다.

바꾸려면 `null_tokens`를 컬럼별로 선언할 수 있어야 하고, 그것은 이 실험의 범위를
넘는 빌더 확장이다.
